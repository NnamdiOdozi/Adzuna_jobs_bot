## Suitability decisions

The deliberately small fixture contains five jobs. One has already been sent and
is removed before model assessment. The remaining four exercise known boundary
cases. Expected decisions below are a manual assessment of those explicit texts,
not labels from an independent representative evaluation dataset.

| Job | Expected | Python rules | Direct Nemotron |
| --- | --- | --- | --- |
| Graduate Finance Analyst | Keep: explicitly requires 0–2 years | Kept | Strong fit, kept |
| Purchase Ledger Clerk | Keep: entry-level finance support with training | Rejected | Possible fit, kept |
| Finance Analyst | Reject: requires five years | Rejected | Unlikely fit, rejected |
| Finance Lawyer | Reject: qualified solicitor required | Kept | Unlikely fit, rejected |
| Graduate Credit Analyst | Suppress: already in history | Suppressed | Removed before assessment |

On the four unseen examples, the rules made 2/4 expected decisions; direct
Nemotron made 4/4. The rules kept 1/2 suitable jobs and 1 unsuitable job. Thus
only 1/2 selected jobs was suitable, and 1/2 suitable jobs was retained. Direct
Nemotron kept 2/2 suitable jobs and no unsuitable ones. These results cannot
establish accuracy on real vacancies: the examples are short, unusually clear
and deliberately target weaknesses already known to us.

The lawyer passed because its title contains `finance`, its category is finance,
no configured title exclusion matches `lawyer`, and its description supplies no
numeric experience minimum above two. The rules do not infer solicitor
qualifications. The ledger role failed because Adzuna rules require a configured
finance term in the title; `Purchase Ledger Clerk` has none, despite clear
finance evidence in its description. JSearch uses a different relevance path.

The agreed lawyer/AVP exclusions were still deferred, not implemented. This is
an unfinished rules improvement, not a new regression introduced by Nemotron.
The synthetic snapshot freezes its original search configuration, so changing
the live configuration alone would not change this particular replay baseline.

## Direct model evidence

The direct call used `nvidia/nemotron-3-super-120b-a12b`. Its saved receipt reports
one call, four candidates, 1,255 input tokens and 1,531 output tokens, totaling
2,786 tokens, taking about 7.4 seconds. All four assessments include matching
evidence quotations. In particular, it quoted `Qualified solicitor required for
banking legal advice.` when rejecting Finance Lawyer.

This establishes that the direct Nebius path worked in this run. It does not
establish model consistency across runs, suitability on ambiguous descriptions,
or GitHub agent runtime compatibility. Matching quotations and valid JSON prove
neither the model's interpretation nor applicant eligibility.

## Agent execution failure

The agent runtime logged that the configured Nemotron model had `no supported
SDK wire API`, then `no models found in awf-reflect endpoints; cannot build
multi-provider config`, and finally that the required BYOK provider could not
be resolved. BYOK means supplying our own model service credential.

This is evidence of a provider-discovery/configuration compatibility failure
between the GitHub agent runtime and the Nebius connection. It is not evidence
of exhausted Adzuna credits, an invalid Nebius key or poor model ranking. The
exact correction needs verification against the runtime implementation before
another paid trial. The workflow already sets a completions wire API variable;
merely setting that same variable again is not a demonstrated fix.

No agent assessment file was produced. Its upload therefore failed, and the
conclusion recorded incomplete execution. Those are consequences of the earlier
runtime abort. The comparison still validated and saved the successful direct
result, sent the requested test email, then deliberately failed its final step
to keep the requested agent failure visible. There is no successful agent
ranking to score, and no basis for assuming that branch incurred zero charges.
